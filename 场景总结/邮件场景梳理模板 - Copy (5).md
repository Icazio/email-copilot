# 邮件场景梳理模板

用于整理每一类邮件的处理流程、查单规则、回复目标和风险边界。  
建议每个场景单独复制一份填写。

---

# 场景名称

示例：
- 退款申请
- 取消续订
- 发票申请
- 注册码无法使用
- Paddle 通知邮件
- 技术问题升级

---

# 1. 场景定义

这一类邮件是什么问题，适用于哪些情况：

```text
请填写
```

---

# 2. 识别信号

看到哪些信号，就可以判断它属于这一类：

```text
关键词：
发件人：
邮件正文固定格式：
订单状态：
其他信号：
```

示例：

```text
关键词：refund / cancel / invoice / license key
发件人：assist@paddle.com
正文格式：customer email: xxxx@example.com
```

---

# 3. 必须提取的信息

这类邮件必须拿到哪些字段，才能继续处理：

```text
- customer email
- order id
- product
- purchase date
- license key
- issue description
- 其他：
```

---

# 4. 需要查询的内容

客服处理这一类邮件时，需要去查什么：

```text
- 是否需要 OrderSearch：
- 是否需要查看历史邮件：
- 是否需要查看共享文档：
- 是否需要查看 Redmine：
- 是否需要查看技术支持平台：
- 是否需要人工确认：
```

---

# 5. 决策规则

根据已提取信息和查询结果，下一步如何判断：

```text
规则 1：
规则 2：
规则 3：
```

示例：

```text
规则 1：如果没有 order id，先追问，不直接处理退款。
规则 2：如果发件人是 Paddle，customer email 优先取正文里的 customer email:。
规则 3：如果是技术问题，只收集信息并升级，不承诺修复时间。
```

---

# 6. 回复目标

这类邮件的回复希望达到什么目的：

```text
- 安抚客户
- 索要必要信息
- 解释政策
- 告知已提交技术团队
- 给出下一步
- 其他：
```

---

# 7. 禁止事项 / 风险点

这类邮件绝对不要怎么回：

```text
- 不承诺退款
- 不承诺修复时间
- 不确认根因，除非有明确证据
- 不暴露内部判断
- 不把系统邮箱当 customer email
- 其他：
```

---

# 8. 标准查询流程

建议按客服真实操作顺序填写：

```text
1. 打开邮件
2. 判断场景
3. 提取字段
4. 查询订单/历史记录
5. 判断下一步
6. 生成回复
7. 是否需要升级
```

---

# 9. 标准回复结构

这一类邮件的回复通常分几段，每段做什么：

```text
第一段：
第二段：
第三段：
```

示例：

```text
第一段：礼貌回应客户
第二段：说明当前判断或需要补充的信息
第三段：给出下一步或结束语
```
