# Naive Bayes 垃圾邮件检测库评估报告

## 背景

在为 Email Copilot 扩展设计垃圾邮件识别功能时，我们调研了三个主流的纯 JavaScript Naive Bayes 分类库，作为替代现有关键词匹配引擎的候选方案。

---

## 候选库

### 1. bayes（ttezel）
- **仓库**：https://github.com/ttezel/bayes
- **Stars**：566（三者中最高）
- **许可证**：MIT

### 2. nbayes（derhuerst）
- **仓库**：https://github.com/derhuerst/nbayes
- **Stars**：16
- **许可证**：ISC
- **包体积**：~3 KB（最轻量）

### 3. credulous（jergason）
- **仓库**：https://github.com/jergason/credulous
- **Stars**：43
- **许可证**：MIT
- **特点**：明确提供浏览器独立文件下载

## 工作原理

Naive Bayes 分类器基于贝叶斯定理，通过统计词语在 spam/ham（正常邮件）两类训练集中出现的概率，推断新邮件属于哪一类：

```
P(spam | 邮件内容) ∝ P(spam) × ∏ P(词 | spam)
```

使用流程：
1. 调用 `classifier.learn(text, "spam")` / `classifier.learn(text, "ham")` 喂入训练数据
2. 调用 `classifier.classify(text)` 对新邮件分类
3. 分类结果随训练数据量的增加而持续改善

---

## 优点

- **纯 JS，无依赖**：可作为单个文件嵌入浏览器扩展，符合本项目零依赖原则
- **增量学习**：客服可在日常操作中持续标注，模型自动进化
- **可解释性强**：Naive Bayes 的概率输出直观，便于调试
- **体积极小**：nbayes 约 3 KB，对扩展包体积几乎无影响

---

## 代价与放弃原因

### 核心问题：没有预训练模型

所有三个库均为**空模型**，必须从零开始训练。这意味着：

| 需求 | 说明 |
|---|---|
| 标注数据量 | 通常需要数百至数千封已标注的 spam/ham 样本才能达到可用精度 |
| 冷启动问题 | 初始阶段无历史数据，准确率极低，甚至不如简单关键词匹配 |
| 数据收集成本 | 需要人工整理并导出现有工单中的 spam/ham 样本，耗时较高 |
| 持久化机制 | 训练结果必须序列化存储（localStorage 或后端），扩展每次重载后需重新加载模型 |

### 次要问题

- 三个库**维护活跃度低**（最近一次提交均在 2022 年之前），社区支持有限
- 纯文本 Naive Bayes 对**短文本**（邮件主题行）的效果不如对长正文，而队列页只显示主题
- 不支持发件人域名、格式特征（全大写、感叹号数量）等非词语信号，而这些信号在本场景中很有区分度

---

## 结论

当前场景（工单主题行 + 发件人邮箱，短文本，冷启动）更适合**加权规则评分引擎**：

- 无需训练数据，立即可用
- 规则透明可控，误判时易于调整
- 可叠加多类信号（关键词、发件人模式、文本风格）

Naive Bayes 方案保留为**长期优化选项**：待积累足够标注数据后可作为评分引擎的补充层引入，提升对未知模式的泛化能力。
